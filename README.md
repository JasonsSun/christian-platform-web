## 一、项目是什么

一个为中文教会与信徒群体打造的**内容传播 + 社交社区**平台，把日常信仰生活里分散的几件事收拢到一处：

读经、灵修、诗歌、讲道、团契小组、活动报名、代祷、直播 —— 以及支撑这些内容流转的发布、审核、通知与管理后台。

它不是内容聚合站，也不是单一功能的小工具，而是一套**可自主部署、可长期运营**的社区基础设施：任何一间教会、一个团契或一支服侍团队，拿到代码就能在自己的服务器上跑起来，数据完全归属自己。

- **线上实例**：`https://amen.dpdns.org`
- **形态**：Web（响应式 + PWA，可添加到手机桌面）；目前无独立 App

## 三、技术架构

### 当前形态（单台 VPS 全栈）

```
浏览器 ──▶ nginx(80/443) ──▶ Next.js 14 App Router(3000) ──▶ MySQL 8(3306)
                                    │
                                    ├── 自研实时总线（WebSocket，ws）
                                    ├── ffmpeg 异步转码 → HLS
                                    └── 存储抽象层 → 本地磁盘 或 S3 兼容对象存储
直播旁路：OBS ──RTMP──▶ MediaMTX ──HLS──▶ 浏览器（hls.js）
```

### 目标架构：四层分离

项目涉及**音视频与直播**，把所有东西压在同一台 VPS 上不是长期方案。合理的做法是按**负载性质**拆分 —— 因为它们的瓶颈完全不同：Web 与数据库吃内存与 IOPS，媒体文件吃存储容量，转码与推流吃 CPU 和出口带宽，备份则要求"不在同一块磁盘上"。

```
                        ┌─────────────────────────────┐
   浏览器/CDN  ─────────▶│  ① 应用节点（Linux VPS）     │
                        │  nginx → Next.js 14 → MySQL8 │
                        │  实时总线（WebSocket）        │
                        └──────┬────────────┬──────────┘
                    媒体读写   │            │  转码/推流任务
                        ┌─────▼──────┐  ┌──▼───────────────┐
                        │ ② 对象存储 │  │ ③ 转码/直播节点  │
                        │ 音频 视频  │  │ ffmpeg → HLS     │
                        │ 封面 附件  │  │ MediaMTX(RTMP→HLS)
                        │ (S3 兼容)  │  └──────────────────┘
                        └─────┬──────┘
                   定时快照   │   ┌──────────────────────┐
                              └──▶│ ④ 备份存储（异地）    │
                                  │ DB + 元数据 + 资料   │
                                  └──────────────────────┘
```

| 层 | 职责 | 承载内容 | 瓶颈资源 | 代码现状 |
|---|---|---|---|---|
| ① 应用 + 数据库 | 网站、API、数据库、实时通信 | 业务数据、会话、通知 | 内存 / IOPS / 连接数 | ✅ 生产运行中 |
| ② 对象存储 | 媒体文件持久化 | 诗歌音频、讲道音视频、封面、附件 | 存储容量 + 下行流量 | ✅ 抽象层已实现，**改一个环境变量即可启用** |
| ③ 转码 / 直播 | 高强度计算与推流 | ffmpeg 转码、RTMP 收流、HLS 分发 | CPU / 出口带宽 | ✅ 已实现；可与应用同机，也可独立 |
| ④ 备份存储 | 容灾 | 数据库 SQL、应用快照、关键资料 | 容量（要求异地） | ✅ 脚本 + 后台备份页已实现，异地存放需配置 |

**为什么这样分**：四层的成本曲线与扩展方式各不相同，绑在一起就必须按"最贵那层"的标准买整台机器。分开之后，媒体量涨了只加对象存储（按量付费、容量无上限），观看人数涨了只给直播节点加带宽，业务量涨了才升级应用节点 —— **每一分钱都花在真正紧张的地方**。

### 选型

| 层 | 选型 |
|---|---|
| 前端 | Next.js **14.2.15**（App Router）+ React **18.3.1** + Tailwind CSS |
| 服务端 | 同仓 API Routes + 自研服务层（61 个模块），无 ORM，SQL 全参数化 |
| 数据库 | MySQL 8（62 张表，运行时幂等建表与补列，漏迁移也不会 500） |
| 实时 | WebSocket 自研总线（通知、群聊、直播聊天） |
| 媒体 | ffmpeg 转码 → HLS；MediaMTX 接收 RTMP 推流 |
| 存储 | 本地磁盘 或 S3 兼容（零依赖 AWS Signature V4，不增加镜像体积） |
| 朗读 | Edge TTS（node-edge-tts） |
| 推送 | Web Push + Nodemailer 邮件 |
| 支付 | 微信支付 v3（RSA2048 + AES-GCM）、支付宝 RSA2、Stripe、线下转账 |
| 部署 | Docker Compose（`nginx` + `web` + `db` + `mediamtx`），单台 VPS 即可起步 |

**代码位置**：本仓库即唯一可交付实现。历史迭代中另有 Java / NestJS 的平行原型，均不再维护，勿使用。

## 四、部署说明

> 完整步骤见 [`DEPLOY.md`](./DEPLOY.md)，直播专项见 [`LIVE-STABILITY.md`](./LIVE-STABILITY.md)。

### 分层容量建议

| 层 | 起步配置 | 随什么增长 | 何时应独立 |
|---|---|---|---|
| ① 应用 + 数据库 | 2 核 4G / 40G SSD | 日活、请求量、数据量 | 磁盘被媒体占满，或转码拖慢页面响应 |
| ② 对象存储 | 50G 起，按量付费 | 媒体存量与下载量 | **现在就能切** —— 不增加运维负担 |
| ③ 转码 / 直播 | 起步可并入 ①；独立则需 4 核 8G 起 | 并发观众数、上传转码量 | 直播卡顿，或转码任务排队 |
| ④ 备份 | 100G，异地 | 数据量 | 一开始就该有（最低成本：应用内快照 + 定期异地拷贝） |

> 带宽按观看人数估算：单路 720p 约 2~4 Mbps/观众；这层压力应由 ② ③ 承担，不该压在应用节点上。

### 快速部署（单台 VPS 起步）

```bash
# 1. 一台 Ubuntu 22.04/24.04 或 Debian 12 的 VPS，放行 22/80/443（直播另需 1935）
curl -fsSL https://get.docker.com | sudo sh

# 2. 拉取代码
sudo mkdir -p /opt && cd /opt
git clone <本仓库地址> christian-platform
cd christian-platform

# 3. 配置环境变量
cp deploy/env.example .env
openssl rand -base64 48          # 作为 JWT_SECRET
nano .env                        # 填 DB_PASSWORD 与 JWT_SECRET

# 4. 启动（nginx + web + db + mediamtx 容器）
docker compose up -d --build
docker compose logs -f web       # 看到"服务器已就绪"即可，Ctrl+C 退出
```

架构上只有 nginx 对公网开放，应用与数据库都在 Docker 内网，**不要放行 3000/3306**。

### 把媒体迁到对象存储

这是四层里**性价比最高、改动最小**的一步 —— 应用代码完全不用动，只需在 `.env` 里设置：

```bash
STORAGE_PROVIDER=s3
S3_BUCKET=your-bucket
S3_REGION=oss-cn-hangzhou
S3_ENDPOINT=oss-cn-hangzhou.aliyuncs.com   # 不含协议与 bucket 前缀
S3_ACCESS_KEY=...
S3_SECRET_KEY=...
S3_PUBLIC_URL=https://cdn.example.com      # 可选，缺省推导为 https://{bucket}.{endpoint}
S3_PATH_STYLE=1                            # 可选，MinIO 等自部署需要
```

改完重启容器即可。历史上传的文件仍是本地路径，可整体同步到 bucket 后保持一致。
配置 CDN 见 [`deploy/cloudflare-cdn.md`](./deploy/cloudflare-cdn.md)。

### 更新与备份

```bash
# 更新（源码改动必须重建镜像，不能只重启容器）
git pull && docker compose up -d --build web

# 备份：应用内 JSON 快照 + 数据库 SQL 定时备份
#   deploy/backup.sh            — 手动/定时执行
#   deploy/install-backup-cron.sh — 安装定时任务
#   /admin/backups              — 后台备份与恢复
```

> 备份务必**挪出应用节点**（拷贝到 ④ 的对象存储/另一台机器）。备份与源数据同盘，等于没有备份。

### 关键环境变量

| 变量 | 用途 |
|---|---|
| `JWT_SECRET` | 令牌签发密钥，**必填强随机串**（弱密钥会拒绝签发 → 登录 500） |
| `DB_PASSWORD` | MySQL 密码 |
| `STORAGE_PROVIDER` | `local`（默认）或 `s3` —— 四层架构里 ② 的开关 |
| `S3_*` | 对象存储的 bucket/region/endpoint/密钥 |
| `MEDIAMTX_PUBLIC_HOST` | 对外推流域名（需 DNS only，不能套 CDN） |
| `REDIS_URL` | 可选；配置了且装有 ioredis 时限流走 Redis，否则走 MySQL 共享计数（多副本同样生效） |

> 多副本部署时，限流、媒体任务接管、全文索引补齐都已做共享存储与乐观锁处理，不会因多实例而错乱。

## 七、路线图与后续维护

### 基础设施演进（四层分离路径）

| 阶段 | 动作 | 收益 | 触发条件 |
|---|---|---|---|
| **阶段 0**（当前） | 单台 VPS 承载全部：nginx + 应用 + MySQL + MediaMTX + 本地磁盘 | 成本最低，运维最简单 | — |
| **阶段 1** | 媒体外置：启用 `STORAGE_PROVIDER=s3` | VPS 磁盘压力立刻释放；媒体容量不再受机型限制；改动仅一个环境变量 | **立即可做**，也是投入产出比最高的一步 |
| **阶段 2** | 转码与推流分离：ffmpeg/MediaMTX 移到独立节点，或改用云转码 | 转码不再抢占应用 CPU；直播卡顿与页面变慢解耦 | 直播常态化，或转码任务开始排队 |
| **阶段 3** | 应用水平扩展：多副本 + 共享存储（MySQL 计数 / Redis）+ 数据库读写分离 | 可承载更大规模访问；单点故障影响下降 | 日活持续增长，单机成为瓶颈 |

> 限流、媒体任务接管、全文索引补齐这三处**已经按多副本设计好**（MySQL 共享计数 + 乐观锁），
> 走到阶段 3 时不需要回头重构。
